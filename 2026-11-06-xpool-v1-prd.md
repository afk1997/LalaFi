## 0. Summary

**What it is.** xpool is one shielded pool shared by several chains. A user deposits USDC on Ethereum, Base or Arbitrum and later withdraws on any of the three. Nothing on-chain links the deposit to the withdrawal. Inside the pool, users can also send each other private transfers.

**What stays from the original spec:**

- the Tornado Nova-style join-split circuit
- one global Merkle tree and one global nullifier set
- an open, stake-weighted validator set with quorum rules R1–R3 ("bigger amounts need more stake")
- relayers, LPs and a CLI wallet

**What changes, and why it matters:** the hub moves onto Ethereum, and the rollups' own official bridges check every cross-chain message. Validators are no longer trusted for safety. They become a *fast lane* that makes Base and Arbitrum deposits usable in about 30 minutes instead of about a week. A validator's exposure clears only when the official bridge confirms what it signed. As a result, a coalition of any size loses more stake than it can take (Section 9.4).

**What v1 delivers:**

1. Deposit on Ethereum, Base or Arbitrum. Spend from one global anonymity set. Withdraw to any of the three chains, with the destination picked at spend time.
2. Join-split spends: full and partial withdrawals, private transfers, merges, and fee-only spends.
3. Groth16 proofs over BN254, verified once, on Ethereum.
4. Payouts to Base and Arbitrum delivered through the official bridges in minutes.
5. Two deposit lanes for Base and Arbitrum:
   - **Fast lane:** validators vouch for the deposit, about 15–30 minutes.
   - **Slow lane:** official bridge only, no validators involved. Takes minutes to about 7 days depending on the chain.
6. An open validator set:
   - Anyone can bond USDC on Ethereum.
   - Quorums are stake-weighted and exposure is capped and cumulative.
   - Every fault can be proven and slashed on Ethereum.
7. Relayers, so users never submit a spend from their own address. The relayer is paid inside the proof.
8. LPs, an insurance fund, and USDC rebalancing between chains through Circle's CCTP.
9. Software:
   - TypeScript SDK and CLI wallet
   - relayer
   - validator node
   - finalizer (carries checkpoints across the bridges)
   - rebalancer keeper
10. A full test suite (circuit, unit, fuzz, invariant, integration, adversarial), plus local, testnet and mainnet configurations. The team does the deployment.

**Key decisions**

| Decision | v1 choice | Why |
|---|---|---|
| Hub location | Ethereum L1. The hub also acts as the Ethereum spoke | Every L2 can verify messages from L1 with no added trust, which removes the md's F4 and F5 faults. No separate hub chain to run or secure |
| Spoke chains | Base (OP Stack) and Arbitrum One (Nitro) | Covers both major rollup bridge families |
| Asset | Native USDC on all three chains | Same token everywhere. Moving it with CCTP adds no trust beyond holding USDC itself |
| Proof system | Groth16 over BN254 (circom 2, snarkjs) | Cheapest verification on Ethereum. Builds on the Tornado Nova circuits |
| Cross-chain verification | Official bridges: OP Stack messengers; Arbitrum inbox, retryables and outbox | No new trust assumptions |
| Validators | Fast lane for L2 deposits. Stake is USDC bonded on Ethereum | Speed without being trusted for safety |
| Upgradeability | None. The guardian can pause new inflows and run one time-limited spend circuit breaker | No key can take funds or block exits for long |

## 1. Goals, non-goals, anti-goals, acceptance

### 1.1 Goals

| ID | Property | Definition in v1 | Origin |
|---|---|---|---|
| G1 | Unlinkability | The on-chain record of any spend reveals nothing beyond the leakage function ℒ (Section 4.5). The zero-knowledge proof hides which notes were spent | md G1 (definition tightened) |
| G2 | Global single spend | Each note is spent at most once, across all chains | md G2 |
| G3 | Balance | Total value paid out never exceeds total value paid in (deposits + LP capital + slashed stake) | md G3 |
| G4 | Destination freedom | The destination chain is chosen at spend time and bound into the proof | md G4 |
| G5 | Non-malleability | A proof can't be redirected to another recipient, chain, amount, fee, relayer, deadline or hub deployment | md G5 |
| G6 | Bounded validator damage | For **any** coalition of validators, of any size, the protocol's loss from their signatures is fully covered by the stake slashed from them | md G6, now actually true |
| G7 | Open participation | Anyone can become a validator (subject to s_min and eviction rules), relayer, LP, finalizer or keeper. No incumbent approval | md G7, now actually true |
| G8 | Reproducibility | Every claim in this document has a test anyone can run locally | md G8 |
| G9 | Liveness without validators | Even if every validator is offline or censoring, users can still deposit and withdraw on every chain (slow lane) | new |
| G10 | No admin custody | No key can move user funds or change verification. No key can block withdrawals for more than 72 hours (Section 7.9) | new |
| G11 | Mainnet-grade | Testnet and mainnet run the same code; only parameters and addresses differ | new (team requirement) |

### 1.2 Non-goals for v1

- Hiding amounts where money enters and leaves the pool. Deposit and withdrawal amounts stay public, as in Tornado Nova.
- Network-level anonymity beyond built-in Tor support in the client.
- Multiple assets, or receiving a different asset than you deposited (e.g. ETH in, USDC out).
- Non-EVM chains and Bitcoin.
- Compliance features such as association sets. These are a v2 candidate.
- A web UI. v1 ships a CLI and an SDK.
- The research paper.

### 1.3 Anti-goals

v1 has failed, even if it runs, if any of these is true:

- Any security claim in this document is false.
- Any admin key can move user funds, or block withdrawals for longer than the bounded circuit breaker.
- The default wallet behavior lets a user link their deposit to their withdrawal without an explicit override (same address, instant withdrawal, exact amounts).
- A user's funds can be stuck forever with no permissionless way out.
- Testnet and mainnet need different code.

### 1.4 v1 acceptance criteria (definition of done)

1. **[P0]** All P0 requirements are implemented, and every test in Section 15 passes in CI.
2. **[P0]** `docker compose up` brings up three local chains and every service. The E2E script passes deposit, transfer and withdrawal for every chain pair, on both deposit lanes.
3. **[P0]** After the team deploys to Sepolia, Base Sepolia and Arbitrum Sepolia, the testnet E2E matrix (Section 15.6) passes. The Base slow lane completes after the Base Sepolia withdrawal delay (about 7 days).
4. **[P0]** The adversarial suite (Section 15.5) shows net protocol loss ≤ 0 after slashing in every collusion scenario, including 100% of validators colluding.
5. **[P0]** Invariant fuzzing runs at least 1,000,000 calls per invariant with no violation.
6. **[P0]** Constraint count, proving time and gas are measured and published (Section 15.8).
7. **[P1]** The privacy measurement (Section 12.2) is published, including global pool vs. separate per-chain pools.
8. **[P0]** The peer validation package (Section 15.9) is published.

## 2. What changed from the original spec

Every mechanism in the original md is listed below with its v1 status. "Superseded" means a v1 mechanism now does the same job, more safely.

| Original md item | v1 status | Reason |
|---|---|---|
| Hub on its own chain (Anvil, later CometBFT) | **Changed:** hub on Ethereum | Spokes can verify L1 messages through the official bridges. No new consensus to trust |
| Spokes: Ethereum + Arbitrum, or Ethereum + Base | **Changed:** Ethereum (inside the hub), Base and Arbitrum | Covers both rollup bridge families, with three chains in one anonymity set |
| Global tree, nullifiers, join-split circuit, note format | **Kept and hardened** | extData now binds the hub's identity, a deadline and explicit fee fields. The hub recomputes every deposit commitment itself. Input amounts are range-checked too |
| Validators attest deposits (R1–R3) | **Kept**, as the fast lane for L2 deposits | Exposure is now *cumulative* and clears only on canonical confirmation. This closes the "sign many times, lose stake once" hole |
| Validators sign releases (R1–R3), fast limit, 30 min / 2 h / 24 h windows | **Superseded** by canonical L1→L2 delivery (1–15 min) | A validator-signed payout can't be both faster and safe. Signing before L1 finality allows reorg double-spends. Signing after finality (about 13 min) is slower than the official bridge on Base and no faster on Arbitrum |
| F1: deposit equivocation | **Kept**, checked on Ethereum | |
| F2: fake deposit | **Kept**, now checked on Ethereum against the canonical checkpoint, where the damage actually happens | |
| F3, F4 (release faults) | **Eliminated** | Validators never sign releases |
| F5 (epoch-update fault) | **Eliminated** | The validator set lives only on Ethereum |
| Veto (ρ = 1/6) | **Superseded** | Nothing is left to veto, and the old veto was a free freeze |
| Stake = LP shares bonded on spokes | **Changed:** USDC bonded on Ethereum, separate from pool liquidity, with per-chain allocations | Stake must not lose value when the pool it guards is attacked. Slashing must happen where fraud is proven |
| New validator set signed by 2/3 of the old set | **Changed:** the set is computed on-chain from bonds, with stake-based eviction | Truly open participation |
| Strict in-order deposit insertion | **Changed:** deposits can be inserted in any order (bitmap) | Removes the "one deposit blocks a chain forever" bug |
| LPs on each spoke | **Changed:** LPs deposit on Ethereum and get global LP shares; CCTP moves liquidity | LPs always get repaid, and no funds are stranded |
| Liquidity imbalance (parked in the md) | **Added:** liquidity ledger, reservation at spend time, CCTP rebalancing | Without these, withdrawals can get stuck |
| A single `fee` field | **Changed:** separate `relayerFee` and `protocolFee`; fee-only spends allowed | In the md, the protocol fee went to the relayer and transfers couldn't pay a fee |
| Validator rewards per release, split among whichever signers were included | **Changed:** paid per epoch, pro rata to stake | The submitter can no longer choose who gets paid |
| Slashed stake: 50% to the watcher | **Changed:** the loss is covered first; the prover reward is capped by ω | The pool must be made whole |
| Escape hatch (planned for v2) | **Not needed** | Hub on Ethereum plus the slow lane means no validator dependency |
| 16-input merge circuit | **Deferred [P2]** | |
| Dynamic fee curve | **Deferred [P2]** | |
| BLS signature aggregation | **Deferred [P2]** | v1 caps the validator set at 32 |
| Association sets | **Deferred [P2]** | |
| Privacy metric k (counting leaves) | **Changed:** metric based on where deposits came from (provenance), plus entropy | Leaves with hidden amounts can't be counted meaningfully |
| Paper deliverables | **Deferred** | Team request |

### 3.3 Lanes

**Deposit lanes**

| Lane | Where | How the leaf gets into the tree | Trust |
|---|---|---|---|
| L1 direct | Ethereum | `DepositManager.deposit` computes the commitment and inserts it in the same transaction | None (same chain) |
| L2 fast | Base, Arbitrum | Validators attest finalized deposits, and the hub inserts them at once. Validator exposure is held until the canonical checkpoint confirms | Covered by stake (Section 9) |
| L2 slow | Base, Arbitrum | Inserted when the canonical checkpoint is processed on Ethereum | None beyond the rollup |

Validators MAY attest any L2 deposit at or below `maxFastDeposit`. Deposits they don't attest, for any reason, are inserted through the slow lane automatically. A deposit can never get stuck.

**Release lanes**

| Destination | How |
|---|---|
| Ethereum | Paid inside `transact`, in the same transaction |
| Base, Arbitrum | `transact` logs the release and sends it through the official bridge. The spoke pays on arrival |

### 3.4 Who can do what

| Party | Can | Cannot |
|---|---|---|
| User | Deposit; spend their own notes | Spend someone else's notes, double-spend, create value |
| Relayer | Delay or drop a spend (the user retries with another relayer) | Change the recipient, amount, chain, fees or deadline |
| Validator coalition (any size) | Insert fake L2 deposits worth at most stake/k, and then lose all its stake. Slow the fast lane (the slow lane still works) | Cause a net loss; block withdrawals; touch releases |
| Finalizer or keeper | Delay checkpoints or rebalances (anyone else can do the same job) | Change any message |
| Guardian (team Safe) | Pause new inflows; trigger one 72-hour spend circuit breaker per 30 days | Move funds; change the verifier or parameters; pause exits beyond 72 hours |
| Rollup official bridges | Trusted, the same way every user of that rollup trusts them | — |
| Circle (USDC, CCTP) | Freeze USDC; delay CCTP | Trusted as the issuer. This risk is accepted |

## 4. Threat model, assumptions and security properties

### 4.1 Actors and what each one sees

| Actor | Role | Sees |
|---|---|---|
| User | Deposits, transfers, withdraws | Their own notes (amounts, blindings, leaf indices) |
| HubCore and DepositManager (Ethereum) | Global tree, nullifiers, proof verification, release log, deposit intake | Proofs, nullifiers, commitments, public amounts, extData |
| Spoke (L2) | Holds USDC on its chain; takes deposits; executes releases | Deposit (owner digest P, amount, depositor), releases |
| Validator | Attests finalized L2 deposits | Only public data |
| Relayer | Submits spends and pays gas, for a fee | Proof, extData, and the user's IP unless Tor is used |
| Finalizer | Carries checkpoints across bridges; redeems or resends messages | Only public data |
| Keeper | Rebalances through CCTP; completes CCTP mints | Only public data |
| LP | Supplies liquidity on Ethereum | Public balances |
| Guardian | Emergency controls with hard limits (Section 7.9) | Only public data |

### 4.2 Adversary model

- **Global passive observer.** Sees every transaction on every chain, forever. Goal: link deposits to withdrawals, or learn balances and transfer graphs.
- **Malicious users.** Try to double-spend, forge notes, inflate amounts, replay or redirect proofs, or grief other users.
- **Validator coalition.** Controls any fraction f ∈ [0, 1] of stake. Can sign anything, withhold signatures, equivocate and censor.
- **Malicious relayers, finalizers and keepers.** Can drop, delay or reorder anything they handle.
- **Reorgs.** L1 can reorg until finality; each L2 can reorg until its finalized head.
- **Network adversary.** Sees IP addresses at RPC endpoints and relayers.

Out of scope: breaking Ethereum consensus, a rollup's proof system, Circle, or the cryptographic assumptions below.

### 4.3 Assumptions

| ID | Assumption |
|---|---|
| A1 | Poseidon (circomlib parameters, BN254) is collision-resistant and preimage-resistant, and behaves like a random oracle for hiding |
| A2 | Groth16 over BN254 is knowledge-sound and zero-knowledge, given at least one honest phase-2 contributor (Section 6.7) |
| A3 | Keccak-256 is collision-resistant; ECDSA over secp256k1 is unforgeable; X25519 + XSalsa20-Poly1305 is IND-CCA secure |
| A4 | Ethereum finalizes, and includes transactions within a bounded delay |
| A5 | The official bridges of Base (OP Stack fault proofs) and Arbitrum (BoLD) eventually deliver exactly the messages that were sent. L2 force-inclusion keeps L2 deposits and checkpoints censorship-resistant |
| A6 | USDC and CCTP behave as Circle specifies. Circle can freeze funds; this is an accepted risk |
| A7 | At least one honest party eventually runs a relayer, a finalizer and a keeper. Anyone can |

**No assumption about the fraction of honest validators is needed for safety.** Only the fast lane's liveness needs at least θ of the stake allocated to a chain to be online and honest.

### 4.4 Security properties

**S1. Balance (G3).** In every reachable state:

$$\sum_{\text{spends } s} v_s \;\le\; \sum_{\text{inserted deposit leaves } \ell} a_\ell, \qquad v_s = w_s + f^{rel}_s + f^{prot}_s$$

*Argument.*
- Each spend consumes two input notes and creates two output notes, with $\sum a_{in} = \sum a_{out} + v$ holding as an integer equation. Range checks on all four amounts make the modular equation an integer one (Section 5.11).
- Nullifier uniqueness means each leaf is consumed at most once.
- By induction: (value of unspent leaves) + Σ v = Σ (deposit leaf amounts).
- The hub computes every deposit leaf's commitment itself from the attested or canonical amount, so a leaf can't claim more than its recorded amount.
- Fraudulent fast-lane leaves appear on the right-hand side. Their value is covered by slashing (S5).

**S2. Spend authority.** Only the holder of sk can spend a note whose owner key is pk = H₁(sk).
*Argument:* knowledge soundness of Groth16 lets an extractor recover sk from any accepted proof. Preimage resistance of Poseidon means only the key holder can know it.

**S3. Global single spend (G2).** The nullifier is a deterministic function of (sk, C, i) (Section 5.5). HubCore keeps one nullifier set for all chains and rejects repeats. Destination releases come only from HubCore's log, so a second spend of the same note can never produce a second release.

**S4. Non-malleability (G5).** extDataHash is a public input. It binds: hub chain id, hub address, destination chain, recipient, withdrawal amount, relayer, both fees, deadline and both encrypted outputs. Changing any of these invalidates the proof (Section 5.7).

**S5. Bounded validator damage (G6).** For any set A of validators, fraudulent value inserted through their signatures satisfies F_A ≤ S_A / k at all times. Every fraudulent batch is eventually proven, and all of its signers' stake is slashed. The stake that backs unconfirmed exposure can't be withdrawn. The protocol therefore never takes a net loss. See Theorem 9.4.

**S6. Release integrity.** A spoke executes a release only when it comes from the official bridge with HubCore's adapter as the authenticated cross-domain sender. Each (destination, index) pair executes at most once.

**S7. Liveness without validators (G9).** The slow lane and canonical releases need only the official bridges plus any finalizer or keeper. With every validator offline, deposits and withdrawals still complete.

**S8. Bounded admin (G10).** The guardian's powers are exactly those in Section 7.9. None of them moves funds or changes verification. Exits can be paused for at most 72 hours per 30 days.

**S9. Unlinkability (G1).** Let ℒ be the leakage function (Section 4.5). There is a simulator that, given only ℒ, produces spend transcripts that no efficient adversary can tell apart from real ones. This follows from:
- the zero-knowledge property of Groth16,
- the hiding of output commitments (fresh blinding b; A1),
- nullifiers being pseudorandom without sk,
- IND-CCA security of note encryption.

Practical unlinkability then depends on what ℒ reveals, which Section 12 measures.

### 4.5 Leakage function ℒ (exactly what is public)

| Event | Public | Private |
|---|---|---|
| Ethereum deposit | Depositor address, amount a, time, owner digest P, encrypted note, leaf index | Owner key pk, blinding b, future spends |
| L2 deposit | Chain, depositor address, amount a, settlement fee, time, P, encrypted note. Later: lane (fast or slow), leaf index | Same as above |
| Spend | Root used; 2 nullifiers; 2 output commitments; 2 encrypted outputs; publicAmount (so v); destination chain; recipient; w; relayer; relayer fee; protocol fee; deadline; time; relayer address as transaction sender | Which leaves were spent; input and output amounts; owners; transfer recipients |
| Release on L2 | Chain, index, recipient, amount, spend id, execution time | — |
| Aggregates | Per-chain liquidity, total value in the pool (`shieldedSupply`), rebalances | Per-user balances |

## 5. Cryptographic specification

### 5.1 Field and encoding

All circuit values live in the BN254 scalar field:

$$p = 21888242871839275222246405745257275088548364400416034343698204186575808495617 \;(\approx 2^{253.6})$$

- On-chain, a field element is a `uint256` strictly below p. **[P0]** Contracts MUST reject any user-supplied field element ≥ p (owner digests, proof public inputs).
- Byte encoding is 32-byte big-endian.
- Keccak outputs used as field elements are reduced mod p. This applies only to extDataHash and the zero leaf.

### 5.2 Hash functions

| Symbol | Function | Parameters | Used for |
|---|---|---|---|
| $H_n$ | Poseidon with n inputs, as in circomlib | t = n + 1, S-box $x^5$, R_F = 8. R_P = 56 (t=2), 57 (t=3), 56 (t=4). Initial state $[0, x_1, \dots, x_n]$; output is state[0]. Constants from circomlib | Keys, notes, nullifiers, Merkle nodes |
| keccak256 | Keccak-256 | — | extDataHash, EIP-712, message hashing, zero-leaf seed. Never used inside the circuit |

Implementations:

| Where | Implementation |
|---|---|
| Circuits | circomlib `Poseidon(n)` |
| SDK | circomlibjs `buildPoseidon` (or `poseidon-lite`, which is compatible) |
| Solidity | `poseidon-solidity` `PoseidonT3` (≈21,124 gas) and `PoseidonT4` (≈37,617 gas) |

`poseidon-solidity` is unaudited according to its README, so it is in the audit scope (Section 16).

**[P0] Cross-implementation test vectors.** CI MUST check that circuit, SDK and Solidity outputs are identical for $H_1$, $H_2$ and $H_3$. Use at least 1,000 random inputs plus edge cases: 0, 1, p−1, and $2^{248}-1$.

**Why there are no explicit domain tags.** The same input layout as Tornado Nova is used. Each hash use either has a different arity, or a fixed position whose preimage structure can't be repurposed:
- Nullifiers can't collide with real notes, because a dummy input's commitment always has a = 0 (Section 5.11).
- Merkle proofs have fixed depth, so a leaf can't be passed off as an inner node.

Adding tags is allowed in v2 but not needed.

### 5.3 Keys and addresses

**[P0] Derivation**

Derive the seed from a 24-word BIP-39 mnemonic (256-bit entropy; optional passphrase): `seed = BIP39_seed(mnemonic, passphrase)`, 64 bytes. Then:

$$sk = \mathrm{OS2IP}\big(\mathrm{HKDF\text{-}SHA256}(seed,\ \texttt{"xpool/v1"},\ \texttt{"spend/"}\Vert acct,\ 64)\big) \bmod p,\qquad sk \neq 0$$

$$pk = H_1(sk)$$

$$encSk = \mathrm{clamp}\big(\mathrm{HKDF\text{-}SHA256}(seed,\ \texttt{"xpool/v1"},\ \texttt{"enc/"}\Vert acct,\ 32)\big),\qquad encPk = \mathrm{X25519}(encSk, 9)$$

- Taking 64 bytes mod p makes the bias negligible (< 2⁻²⁵⁰).
- `acct` is a 32-bit account number, starting at 0.
- `clamp` is the X25519 clamping from RFC 7748.

**Shielded address**

$$\mathsf{addr} = \mathrm{bech32m}\big(\mathrm{hrp},\ \texttt{0x01} \Vert pk_{32} \Vert encPk_{32}\big)$$

- HRP: `xpool` on mainnet, `txpool` on testnet, `lxpool` locally.
- The address can be shared publicly. It reveals nothing about which notes its owner holds.

**Fresh withdrawal addresses.** Fresh EOAs for withdrawal recipients are derived from the same mnemonic at BIP-44 path `m/44'/60'/7331'/0/n`, with n incremented per withdrawal and never reused *(decision)*. They stay separate from the user's everyday Ethereum accounts.

### 5.4 Notes and commitments

A note is $(a, t, pk, b)$:

| Field | Meaning | Domain |
|---|---|---|
| a | Amount in USDC base units | $0 \le a < 2^{248}$. For deposits, `minDeposit ≤ a ≤ maxDeposit` |
| t | Token id | t = 1 (USDC) in v1, a circuit constant. It is in the commitment so multiple assets can be added later without a new tree |
| pk | Owner public key | $H_1(sk)$ |
| b | Blinding | Uniform in $\mathbb{F}_p$: 64 CSPRNG bytes mod p |

$$P = H_2(pk, b) \qquad C = H_3(a, t, P)$$

- Only C enters the tree. P is public for deposits only (it's sent in the deposit call). P hides pk because b is uniform.
- **[P0] The hub computes every deposit commitment itself,** from the deposit's amount and P, using `PoseidonT4`. This holds for Ethereum deposits, fast-lane attestations and canonical checkpoints alike. The hub never accepts a commitment from a validator or user.
  - This binds the note's value to the amount actually recorded.
  - Without it, a validator could attest "1 USDC" while inserting a commitment that is worth a million.
- Output commitments of a spend are computed inside the circuit (Section 6).

### 5.5 Nullifiers

When a note at leaf index $i$ ($0 \le i < 2^{24}$) is spent:

$$\sigma = H_3(sk, C, i) \qquad N = H_3(C, i, \sigma)$$

| Property | Why it holds |
|---|---|
| Deterministic | Same (sk, C, i) gives the same N, so a second spend is caught |
| Unlinkable | Without sk, σ is pseudorandom, so N reveals nothing about C or i (A1) |
| Owner-bound | Only the holder of sk can compute σ |
| Position-bound | Including i means two identical commitments at different leaves are each spendable once. This is the "Faerie Gold" fix from Zcash; see Section 5.11 |

HubCore keeps one global set $\mathcal{N}$. A spend is valid only if both of its nullifiers are outside $\mathcal{N}$ and different from each other. Both are then added.

### 5.6 Global Merkle tree

| Item | Specification |
|---|---|
| Depth | d = 24, which holds 16,777,216 leaves |
| Node hash | $H_2(\text{left}, \text{right})$ |
| Zero leaf | $Z_0 = \mathrm{keccak256}(\texttt{"xpool.v1.zero"}) \bmod p$ |
| Zero subtrees | $Z_{\ell+1} = H_2(Z_\ell, Z_\ell)$ for $\ell = 0..23$. Precomputed and stored as constants; empty root = $Z_{24}$ |
| Insertion | **Pairs only.** `nextIndex` is always even. A batch with an odd number of leaves is padded with $Z_0$ *(decision: same gas as a pair; nobody can spend the padding because finding a preimage of $Z_0$ is infeasible)* |
| Root history | The last 100 roots. Lookup is O(1) via `rootSeq[root]`, accepted if `seq − rootSeq[root] < 100` |
| Capacity | At worst 2 leaves per deposit and 2 per spend. Full-tree behavior: all deposits and spends revert with `TreeFull`; the next version migrates |

**Pair insertion** (from Tornado Nova's `MerkleTreeWithHistory`; it costs d = 24 Poseidon calls). F[ℓ] is the stored frontier:

```
insertPair(l, r):
  require nextIndex + 2 <= 2^d
  idx = nextIndex / 2
  cur = H2(l, r)
  for lvl in 1 .. d-1:
      if idx is even:  F[lvl] = cur;  cur = H2(cur, Z[lvl])
      else:            cur = H2(F[lvl], cur)
      idx = idx / 2
  push cur into root history;  nextIndex += 2
  return nextIndex - 2              // leaf index of l
```

Membership is checked bottom-up. The index bits come from i:

$$h_0 = C,\qquad h_{\ell+1} = \begin{cases} H_2(h_\ell, s_\ell) & \text{if bit}_\ell(i) = 0 \\ H_2(s_\ell, h_\ell) & \text{if bit}_\ell(i) = 1\end{cases},\qquad h_{24} \stackrel{?}{=} \text{root}$$

### 5.7 External data, public amount and fees

**[P0]** Everything about a spend that lives outside the circuit is bound by one public input:

```solidity
struct ExtData {
    uint32  version;          // = 1
    uint64  hubChainId;       // must equal block.chainid of the hub
    address hub;              // must equal HubCore address
    uint64  dstChainId;       // 0 = no withdrawal (transfer / merge / fee-only)
    address recipient;        // must be 0 iff dstChainId == 0
    uint256 withdrawAmount;   // w; must be 0 iff dstChainId == 0
    address relayer;          // receives relayerFee on Ethereum
    uint256 relayerFee;       // multiple of relayerFeeBucket (Section 10.5)
    uint256 protocolFee;      // == ceil(w * phiBps / 10_000)
    uint64  deadline;         // unix seconds; spend invalid after this
    bytes   encOut0;          // <= 256 bytes
    bytes   encOut1;          // <= 256 bytes
}
```

$$\text{extDataHash} = \mathrm{uint256}\big(\mathrm{keccak256}(\mathrm{abi.encode}(\text{ExtData}))\big) \bmod p$$

Total value leaving the pool, and how it is encoded as a field element:

$$v = w + f^{rel} + f^{prot}, \qquad f^{prot} = \Big\lceil \frac{w \cdot \varphi_{bps}}{10^4} \Big\rceil, \qquad \text{publicAmount} = \begin{cases} 0 & v = 0 \\ p - v & v > 0 \end{cases}$$

The hub computes publicAmount itself from ExtData and requires it to equal the proof's public input. It also requires:
- $v < 2^{248}$
- $w \ge$ `minWithdraw` when $w > 0$
- the destination is supported
- `deadline ≥ block.timestamp`

**Deposits never go through `transact`,** so publicAmount is never "positive".

### 5.8 Note encryption

**[P0] Scheme.** NaCl `box` with an ephemeral sender key: X25519 key agreement, HSalsa20 key derivation, XSalsa20-Poly1305 AEAD. This is the same scheme Tornado Nova uses.

```
plaintext  = a (32B BE) || b (32B BE)                               // 64 bytes
esk, epk   = X25519 keypair (fresh per note)
key        = crypto_box_beforenm(encPk_recipient, esk)
nonce      = 24 random bytes
ciphertext = 0x01 || epk (32) || nonce (24) || XSalsa20-Poly1305(key, nonce, plaintext) (80)
                                                                     // 137 bytes total
```

Rules:

- **Scanning.** Wallets trial-decrypt every `encOut` (from HubCore `NewCommitment` events) and every `encNote` (from deposit events on all three chains).
- **[P0] Validate before accepting.** After decrypting, the wallet MUST recompute $C = H_3(a, 1, H_2(pk, b))$ and compare it with the on-chain commitment. Mismatches are ignored, so a garbage ciphertext from a malicious sender can never corrupt a wallet.
- **Recovery.** Change notes are encrypted to the sender's own encPk. A wallet can be fully rebuilt from the mnemonic alone.
- **Dummy outputs.** Zero-value outputs carry an encryption under a random throwaway key, so they can't be told apart from real outputs.

### 5.9 Validator signatures (fast lane)

**[P0]** Validators sign attestations as ECDSA secp256k1 over EIP-712 typed data. The hub accepts only low-s signatures (OpenZeppelin `ECDSA`).

```
EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)
  name = "xpool", version = "1", chainId = hub chain id, verifyingContract = DepositManager

L2Deposit(uint64 index,uint256 ownerDigest,uint256 amount,uint256 fee,uint64 l2Block)
DepositBatch(uint64 srcChainId,address spoke,uint64 epoch,L2Deposit[] deposits)
```

- A validator's signature on a `DepositBatch` claims: *each listed deposit exists on spoke `spoke` of chain `srcChainId`, at the given index, with exactly these fields, in an L2 block at or below the chain's finalized head.*
- A false claim is slashable (Section 9.5). The signing key is registered in StakeManager and kept separate from the operator key that holds the stake.

### 5.10 Randomness

**[P0]** Every random value MUST come from the OS CSPRNG (`crypto.getRandomValues` or `crypto.randomBytes`). This covers b, dummy-input keys, ephemeral X25519 keys, nonces and deadline jitter. Deriving randomness deterministically from the seed is forbidden, except where Section 5.3 says so.

### 5.11 Security arguments

**Binding.** If $H_3(a, t, P) = H_3(a', t', P')$ with $(a,t,P) \neq (a',t',P')$, that is a Poseidon collision (A1). So a commitment opens to exactly one (a, t, P), and through $P = H_2(pk, b)$, to one (pk, b).

**Hiding.** With uniform b, P is indistinguishable from uniform. So C reveals nothing about a or pk (A1, random-oracle model).

**No inflation through field wraparound.** The circuit range-checks all four amounts: $a_0, a_1, a'_0, a'_1 < 2^{248}$. The hub checks $v < 2^{248}$. The circuit enforces $a_0 + a_1 - v \equiv a'_0 + a'_1 \pmod p$. As an integer, $X = a_0 + a_1 - a'_0 - a'_1 - v$ lies in $(-3 \cdot 2^{248},\, 2^{249})$, an interval narrower than $2^{251} < p$. The only multiple of p in that interval is 0, so

$$a_0 + a_1 = a'_0 + a'_1 + v \quad \text{(over the integers)}$$

The circuit also range-checks inputs (an addition over Nova), so this argument doesn't depend on how a leaf was created.

**Dummy inputs.** An input with $a_j = 0$ skips the Merkle check (`ForceEqualIfEnabled`, enabled = $a_j$). It contributes 0 to the sum, and its nullifier is random-looking. For a dummy nullifier to equal a real note's nullifier, the attacker would need $H_3(0, t, P') = H_3(a, t, P)$ with a ≠ 0, which is a collision. So dummies can't burn other people's notes. The SDK MUST generate fresh dummy keys for every spend; a reused dummy nullifier is rejected.

**Faerie Gold.** Two notes with the same commitment at different leaves get different nullifiers, because i is an input to σ and N. Each can be spent once. A sender can't create two notes that only one nullifier can spend.

**Zero-value outputs and padding.** Leaves with a = 0 (dummy outputs) and the $Z_0$ padding leaves can never fund anything. They add to the leaf count but not to anyone's balance.

## 6. Circuit specification

### 6.1 Template

**[P0]** One circuit, `Transaction(levels = 24, nIns = 2, nOuts = 2, TOKEN = 1)`, handles every spend. It is adapted from Tornado Nova's `transaction.circom` to the note format in Section 5, with input range checks added.

### 6.2 Signals

| Signal | Visibility | Meaning |
|---|---|---|
| `root` | public | A root from HubCore's last 100 roots |
| `publicAmount` | public | $p - v$, or 0 (Section 5.7) |
| `extDataHash` | public | Section 5.7 |
| `inputNullifier[2]` | public | Nullifiers of the two inputs |
| `outputCommitment[2]` | public | Commitments of the two outputs |
| `inAmount[2]`, `inSk[2]`, `inBlinding[2]`, `inLeafIndex[2]` | private | Input notes and owner key |
| `inPathElements[2][24]` | private | Merkle sibling paths |
| `outAmount[2]`, `outPk[2]`, `outBlinding[2]` | private | Output notes |

snarkjs orders the public signals as: `[root, publicAmount, extDataHash, inputNullifier[0], inputNullifier[1], outputCommitment[0], outputCommitment[1]]`. That is 7 public inputs.

### 6.3 Constraints

For each input $j \in \{0, 1\}$:

$$pk_j = H_1(sk_j),\quad P_j = H_2(pk_j, b_j),\quad C_j = H_3(a_j, 1, P_j),\quad \sigma_j = H_3(sk_j, C_j, i_j),\quad \text{inputNullifier}_j = H_3(C_j, i_j, \sigma_j)$$

$$a_j < 2^{248}, \qquad i_j < 2^{24}, \qquad a_j \cdot \big(\mathrm{MerkleRoot}(C_j, \text{path}_j, i_j) - \text{root}\big) = 0$$

For each output $k \in \{0, 1\}$:

$$\text{outputCommitment}_k = H_3\big(a'_k,\ 1,\ H_2(pk'_k, b'_k)\big), \qquad a'_k < 2^{248}$$

Then, globally:

$$\text{inputNullifier}_0 \neq \text{inputNullifier}_1, \qquad a_0 + a_1 + \text{publicAmount} = a'_0 + a'_1, \qquad \text{extDataSquare} = \text{extDataHash}^2$$

The square constraint is a no-op guard: it keeps the public input bound even if the compiler would otherwise optimize it away. Reference sketch (circom 2.1.x):

```circom
pragma circom 2.1.9;
include "circomlib/circuits/poseidon.circom";
include "circomlib/circuits/bitify.circom";
include "circomlib/circuits/comparators.circom";
include "./merkleProof.circom";   // Nova's MerkleProof(levels): (leaf, pathElements, pathIndices) -> root

template Transaction(levels, nIns, nOuts, TOKEN) {
    signal input root; signal input publicAmount; signal input extDataHash;
    signal input inputNullifier[nIns]; signal input outputCommitment[nOuts];
    signal input inAmount[nIns]; signal input inSk[nIns]; signal input inBlinding[nIns];
    signal input inLeafIndex[nIns]; signal input inPathElements[nIns][levels];
    signal input outAmount[nOuts]; signal input outPk[nOuts]; signal input outBlinding[nOuts];

    component kp[nIns]; component pd[nIns]; component cm[nIns]; component sg[nIns];
    component nf[nIns]; component tr[nIns]; component eq[nIns]; component rin[nIns]; component ib[nIns];
    var sumIns = 0;
    for (var j = 0; j < nIns; j++) {
        kp[j] = Poseidon(1); kp[j].inputs[0] <== inSk[j];
        pd[j] = Poseidon(2); pd[j].inputs[0] <== kp[j].out; pd[j].inputs[1] <== inBlinding[j];
        cm[j] = Poseidon(3); cm[j].inputs[0] <== inAmount[j]; cm[j].inputs[1] <== TOKEN; cm[j].inputs[2] <== pd[j].out;
        sg[j] = Poseidon(3); sg[j].inputs[0] <== inSk[j]; sg[j].inputs[1] <== cm[j].out; sg[j].inputs[2] <== inLeafIndex[j];
        nf[j] = Poseidon(3); nf[j].inputs[0] <== cm[j].out; nf[j].inputs[1] <== inLeafIndex[j]; nf[j].inputs[2] <== sg[j].out;
        nf[j].out === inputNullifier[j];
        rin[j] = Num2Bits(248); rin[j].in <== inAmount[j];
        ib[j] = Num2Bits(levels); ib[j].in <== inLeafIndex[j];
        tr[j] = MerkleProof(levels); tr[j].leaf <== cm[j].out; tr[j].pathIndices <== inLeafIndex[j];
        for (var l = 0; l < levels; l++) { tr[j].pathElements[l] <== inPathElements[j][l]; }
        eq[j] = ForceEqualIfEnabled(); eq[j].in[0] <== root; eq[j].in[1] <== tr[j].root; eq[j].enabled <== inAmount[j];
        sumIns += inAmount[j];
    }
    component op[nOuts]; component oc[nOuts]; component ro[nOuts];
    var sumOuts = 0;
    for (var k = 0; k < nOuts; k++) {
        op[k] = Poseidon(2); op[k].inputs[0] <== outPk[k]; op[k].inputs[1] <== outBlinding[k];
        oc[k] = Poseidon(3); oc[k].inputs[0] <== outAmount[k]; oc[k].inputs[1] <== TOKEN; oc[k].inputs[2] <== op[k].out;
        oc[k].out === outputCommitment[k];
        ro[k] = Num2Bits(248); ro[k].in <== outAmount[k];
        sumOuts += outAmount[k];
    }
    component same = IsEqual(); same.in[0] <== inputNullifier[0]; same.in[1] <== inputNullifier[1]; same.out === 0;
    sumIns + publicAmount === sumOuts;
    signal extDataSquare <== extDataHash * extDataHash;
}
component main {public [root, publicAmount, extDataHash, inputNullifier, outputCommitment]} = Transaction(24, 2, 2, 1);
```

*(builder's call)* Exact component wiring and how `MerkleProof` takes the index (as a number or as bits) are left to the implementer, as long as the constraints above hold and the negative tests in Section 15.1 fail as expected.

### 6.5 Soundness (mapped to Section 4.4)

| Attack | Blocked by |
|---|---|

### 7.2 Conventions [P0]

- **Toolchain and libraries:** Solidity 0.8.28 (or later 0.8.x), Foundry, OpenZeppelin Contracts 5.x (`SafeERC20`, `ReentrancyGuard`, `ECDSA`, `EIP712`, `Math`).
- **No upgradeability.** No proxies, no `delegatecall` to mutable targets, no `selfdestruct`. Cross-contract and cross-chain addresses are `immutable` constructor arguments, computed in advance with CREATE2 (Section 14.5).
- **Checks–effects–interactions** order, plus `nonReentrant` on every external state-changing function.
- **Errors and events.** Custom errors only. Every state change emits an event that the SDK can index.
- **Input validation.** Every external input is validated: field elements < p, lengths bounded, chain ids from the supported set.
- **Fee rounding.** Integer math rounds against the user for fees and against the protocol for capacity: `Math.mulDiv`, `ceilDiv`.

### 7.4 HubCore

**State.** `nextIndex`, the frontier `F[24]`, the root ring `roots[100]` plus `rootSeq[root]`, `spent[nullifier]`, `shieldedSupply`, `releaseCount[dst]`, `releaseHash[dst][index]`, `spendsPausedUntil`, `lastEmergencyPause`. Immutables: the verifier, the Poseidon libraries, `DepositManager`, `LiquidityManager`, adapters per destination, the supported chain ids, `phiBps`, `relayerFeeBucket`, `minWithdraw[dst]`, `guardian`.

```solidity
interface IHubCore {
    function transact(Proof calldata proof, PublicInputs calldata pi, ExtData calldata ext,
                      BridgeParams calldata bp) external payable;
    function resendRelease(Release calldata r, BridgeParams calldata bp) external payable; // anyone; idempotent on spoke
    function insertDepositLeaves(uint256[] calldata commitments, uint256 totalAmount)
        external returns (uint32 firstLeafIndex);                                       // only DepositManager
    function isKnownRoot(uint256 root) external view returns (bool);
    function isSpent(uint256 nullifier) external view returns (bool);
    function nextLeafIndex() external view returns (uint32);
    function shieldedSupply() external view returns (uint256);
    function releaseCount(uint64 dstChainId) external view returns (uint64);

    event NewCommitment(uint256 indexed commitment, uint32 indexed leafIndex, bytes encryptedOutput);
    event NewNullifier(uint256 indexed nullifier);
    event Spend(bytes32 indexed spendId, uint256 root, uint64 dstChainId, uint256 v);
    event ReleaseLogged(uint64 indexed dstChainId, uint64 indexed index, address recipient,
                        uint256 amount, bytes32 spendId);
}
```

**[P0] `transact` checks, in this order.** Any failure reverts.

1. `block.timestamp ≥ spendsPausedUntil` (circuit breaker; Section 7.9).
2. `ext.version == 1`, `ext.hubChainId == block.chainid`, `ext.hub == address(this)`, `ext.deadline ≥ block.timestamp`, and both `encOut` lengths ≤ 256.
3. Withdrawal shape:
   - If `dstChainId == 0`: then `recipient == 0`, `w == 0` and `protocolFee == 0`.
   - Otherwise: the destination is supported, `recipient ≠ 0`, `w ≥ minWithdraw[dst]` and `protocolFee == ceilDiv(w·φ, 10⁴)`.
4. `relayerFee % relayerFeeBucket == 0`, and if `relayerFee > 0` then `relayer ≠ 0`.
5. `v = w + relayerFee + protocolFee < 2^248`, and `pi.publicAmount == (v == 0 ? 0 : P − v)`.
6. `isKnownRoot(pi.root)`. All 7 public inputs are < P.
7. The two nullifiers differ, and neither is spent.
8. `pi.extDataHash == uint256(keccak256(abi.encode(ext))) % P`.
9. `verifier.verifyProof(proof, [root, publicAmount, extDataHash, n0, n1, c0, c1]) == true`.
10. Liquidity: if `w > 0`, call `LiquidityManager.reserve(dst, w)`. This reverts with `InsufficientLiquidity(dst)` if `L[dst] < w`; the wallet checks this before proving.

**Effects**, after all checks pass:

- Mark both nullifiers spent.
- `insertPair(c0, c1)`.
- `shieldedSupply −= v`.
- `LiquidityManager.accrueProtocolFee(protocolFee)`.
- `LiquidityManager.payRelayer(relayer, relayerFee)`. This pays at once if `L[ETH]` allows; otherwise it credits a claimable balance.
- Emit the events.

**Interactions**, last:

- If `dst == hubChainId`: `LiquidityManager.payOnL1(recipient, w)`.
- Otherwise: `index = releaseCount[dst]++`, store `releaseHash`, then `adapter[dst].sendToSpoke{value: msg.value}(abi.encode(MSG_RELEASE, abi.encode(release)), bp)`.
- `msg.value` MUST be 0 unless the destination's adapter needs ETH (Arbitrum).

**[P0] `resendRelease`.** Anyone can re-send a logged release, by supplying its content and matching `releaseHash`. This covers expired Arbitrum retryables and failed OP messages. The spoke executes each index at most once, so re-sending is always safe.

**[P0] `insertDepositLeaves`.** Only `DepositManager` can call it. It inserts commitments in pairs, padding an odd count with $Z_0$, and adds `totalAmount` to `shieldedSupply`. It returns the first leaf index.

### 7.5 DepositManager

```solidity
interface IDepositManager {
    // Ethereum deposits [P0]

    event L1Deposit(uint32 indexed leafIndex, uint256 commitment, uint256 amount, address depositor, bytes encNote);
    event BatchAttested(uint256 indexed batchId, uint64 indexed srcChainId, uint64 epoch,
                        uint256 totalAmount, uint256 signerBitmap, address submitter);
    event L2DepositInserted(uint64 indexed srcChainId, uint64 indexed index, uint256 commitment,
                            uint32 leafIndex, bool fastLane);
    event CheckpointReceived(uint64 indexed srcChainId, uint64 indexed seq, uint64 from, uint64 to,
                             uint64 countAtSend, uint64 l2Block);
    event DepositConfirmed(uint64 indexed srcChainId, uint64 indexed index);
    event BatchConfirmed(uint256 indexed batchId);

```

**[P0] Ethereum deposit (`deposit`).**

1. Check, in order:
   - inflows are not paused
   - `minDeposit ≤ amount ≤ maxDeposit`
   - `ownerDigest < P`
   - `encNote.length ≤ 256`
   - the Ethereum TVL cap is not exceeded
2. Pull the USDC into the L1 vault.
3. Compute `C = PoseidonT4(amount, 1, ownerDigest)`.
4. `HubCore.insertDepositLeaves([C], amount)`.
5. `LiquidityManager.credit(ETH, amount)`.
6. Emit `L1Deposit`.

**[P0] Fast-lane attestation (`submitAttestation`).**

*Checks:*

1. The fast lane is not paused. The chain is a supported spoke. `epoch ∈ {current, current − 1}` (the grace window tolerates submissions that cross an epoch boundary).
2. `1 ≤ deposits.length ≤ MAX_BATCH` (32).
3. For each deposit:
   - `ownerDigest < P`
   - `minDeposit ≤ amount ≤ maxFastDeposit`
   - `inserted[chain][index] == false`
4. `signers` is strictly ascending, and `sigs.length == signers.length`.
5. Each signer maps to a registered, non-jailed validator with a positive allocation to this chain in `epoch`.
6. Each signature recovers to its signer over the EIP-712 `DepositBatch` digest (Section 5.9).
7. Quorum rules R1, R2 and R3 from Section 9.2, using the stake snapshot for `epoch`.
8. Global safety valve: `unconfirmedFastValue + A ≤ β · (lpAssets + insurance)` (Section 9.6).

*Effects:*

- Store the batch: chain, epoch, `depositsHash`, signer bitmap, $S_Q$, A, item count, confirmed count = 0, status = Pending, submitter.
- Add each signer's exposure $x_v$ through StakeManager.
- For each deposit: `inserted = true`, `fastItem[chain][index] = {batchId, keccak256(abi.encode(d))}`, `C = PoseidonT4(a, 1, P)`.
- Call `HubCore.insertDepositLeaves(Cs, A)`.
- `unconfirmedFastValue += A`.
- Emit the events.
- **Do not** credit `L[chain]`. Liquidity counts only once confirmed.

**[P0] Canonical checkpoint intake (`receiveCheckpoint`).**

- Only the hub adapter for `srcChainId` can call it, after it has authenticated the official bridge (Section 7.8).
- It decodes the payload and checks that `to − from == deposits.length` and `deposits[k].index == from + k`.
- It stores `{payloadHash, from, to, countAtSend, l2Block, nextItem = from}` keyed by `(chain, seq)`, and rejects a duplicate `seq`.
- It does **not** process items. That keeps the bridge's relay call cheap, so it can't run out of gas.

**[P0] Checkpoint processing (`processCheckpoint`).** Anyone can call it, and it can be chunked through `maxItems`. It requires `keccak256(payload) == payloadHash`. Then, for each item d at index i with `h = keccak256(abi.encode(d))`, it handles four cases:

| Case | Action |
|---|---|
| `fastItem[i]` exists and `fastItem[i].hash == h` | Confirm the item. When every item of its batch is confirmed: clear the batch's exposure, `unconfirmedFastValue −= A`, credit the submitter's insertion bounties, emit `BatchConfirmed` |
| `fastItem[i]` exists and `fastItem[i].hash ≠ h` | **Fraud (mismatch).** If the batch is not already marked fraud: `slashBatch(batchId, MISMATCH, msg.sender)`. Then insert the *true* deposit's commitment, so the honest depositor still gets their note (`shieldedSupply += a`) |
| Not inserted yet | **Slow lane.** Insert C; set `inserted = true` |
| Every case | `confirmed[chain][i] = true`; `LiquidityManager.credit(chain, a + fee)`; settlement-fee accounting (Section 10.2) |

- Slow-lane leaves are collected in memory and inserted in pairs at the end of the call.
- A fake leaf that was already inserted stays in the tree. Its value is backed by the slashed stake (Section 9.4), so no leaf ever needs to be revoked.

**[P0] Fraud proofs.**

| Kind | Proven by |
|---|---|
| **Absence** (`proveAbsence`) | A stored checkpoint `cp` and an attested item d in batch b, with `d.index ≥ cp.countAtSend` and `d.l2Block < cp.l2Block`. That means the claimed deposit did not exist at the block it claimed. Slash every signer of b |
| **Equivocation** (`proveEquivocation`) | Two signatures by the same signer, each over a `DepositBatch`, where both include the same `(chain, index)` with different content. Slash that signer. Either batch may never have been submitted on-chain |
| **Mismatch** | Detected automatically during checkpoint processing (above). No separate prover is needed |

**`slashBatch(b)`.** Slash every signer of b in full (Section 9.5), mark b as Fraud, `unconfirmedFastValue −= A_b`, and emit `FraudProven`.

Rules:

- **[P0] Registry.** At most `MAX_VALIDATORS = 32` active validators.
  - When the registry is full, a newcomer whose bond is greater than the smallest active bond plus `evictionMargin` replaces that validator at the next epoch. The evicted validator moves to unbonding and stays slashable.
  - This keeps G7 true: incumbents can't block entry.
- **[P0] Epochs.** `advanceEpoch` is permissionless once `epochLength` has passed. It applies pending bonds, allocations and unbonds; snapshots $s_v^c(e)$ and $S^c(e)$ for every validator and chain (at most 32 × 2 entries); and distributes the epoch's reward pot pro rata to active stake. Attestations must reference a snapshotted epoch.
- **[P0] Exposure coverage.** Any allocation decrease, unbond or eviction that would break $e_v^c \cdot k > s_v^c$ in any epoch where the validator could still sign is rejected, or deferred until the exposure clears.
- **[P0] Slashing.**
  1. `slash` takes the validator's **entire** bonded and unbonding stake, and jails the validator for good.
  2. The prover gets $r = \min(\omega \cdot \Sigma,\ \Sigma - \text{coveredLoss})$.
  3. The rest goes to `LiquidityManager` as insurance: transfer the USDC, then `credit(ETH, ·)`.
  4. Unbonding withdrawals wait until `unlockTime`. Stake stays slashable throughout.

```solidity
interface ISpoke {

    function processQueue(uint256 maxItems) external;          // permissionless

    event ReleaseExecuted(uint64 indexed index, address recipient, uint256 amount);

```

**[P0] Spoke rules:**

- **`deposit`.**
  - Checks: not paused, `minDeposit ≤ amount ≤ maxDeposit`, `ownerDigest < P`, `encNote.length ≤ 256`, TVL cap.
  - Pulls `amount + settleFee` and stores `deposits[index] = {P, amount, fee, l2BlockNumber()}`.
  - Does no Poseidon on L2; the hub computes C.
- **[P0] `l2BlockNumber()`.** On OP Stack this is `block.number`. On Arbitrum it MUST be `ArbSys(address(100)).arbBlockNumber()`, because `block.number` on Arbitrum returns an approximate *L1* block number that several L2 blocks share.
  - Validators MUST attest the `l2Block` value from the `Deposit` event, not the receipt's block number.
  - Checkpoints use the same function, so the absence check (`d.l2Block < cp.l2Block`) always compares readings from the same clock.
- **`sendCheckpoint`.**
  - Sends `MSG_CHECKPOINT` with `seq`, `from = nextCheckpointFrom`, `to = min(depositCount, from + MAX_CHECKPOINT)`, `countAtSend = depositCount`, `l2Block = l2BlockNumber()`, and the data for deposits `[from, to)`.
  - An *empty* checkpoint (`to == from`) is allowed at most once every `minEmptyCheckpointInterval` blocks. It exists so watchers can prove absence.
- **`receiveFromHub`** MUST authenticate the canonical origin (table below) and MUST NOT revert on application errors.
  - **RELEASE:**
    - Require `dstChainId == block.chainid`.
    - If `executed[index]` is already set, ignore (idempotent).
    - Otherwise mark it executed and try to pay. With insufficient balance, queue it. If the USDC transfer fails (for example, the recipient is blacklisted), record it as failed and emit an event.
  - **REBALANCE:** Ignore it if its nonce was already used. Otherwise approve CCTP `TokenMessengerV2` and call `depositForBurn(amount, dstDomain, mintRecipient, USDC, bytes32(0), maxFee, minFinality)`.
  - **PAUSE:** Set the deposit pause flag. Releases are never paused.
- **`processQueue`** pays queued releases first-in-first-out while there is liquidity, for example once a CCTP mint lands.

**[P0] Authenticating the canonical bridge:**

| Direction | OP Stack (Base) | Arbitrum |
|---|---|---|
| Hub → spoke, sending on L1 | `L1CrossDomainMessenger.sendMessage(spoke, abi.encodeCall(ISpoke.receiveFromHub, (msg)), minGasL2)` | `Inbox.createRetryableTicket{value}(spoke, 0, maxSubmissionCost, refund, refund, gasLimit, maxFeePerGas, data)` |
| Hub → spoke, checks on L2 | `msg.sender == 0x4200000000000000000000000000000000000007 && IL2CrossDomainMessenger(msg.sender).xDomainMessageSender() == hubAdapter` | `msg.sender == AddressAliasHelper.applyL1ToL2Alias(hubAdapter)` |
| Spoke → hub, sending on L2 | `L2CrossDomainMessenger.sendMessage(hubAdapter, data, minGasL1)` | `ArbSys(address(100)).sendTxToL1(hubAdapter, data)` |
| Spoke → hub, checks on L1 | `msg.sender == L1CrossDomainMessenger && xDomainMessageSender() == spoke` | `msg.sender == bridge && IOutbox(IBridge(bridge).activeOutbox()).l2ToL1Sender() == spoke` |
| Finalizing on L1 | Prove after a dispute game covers the L2 block, then finalize after the proof maturity delay (`OptimismPortal`) | `Outbox.executeTransaction(proof, …)` after the assertion is confirmed |

For the Arbitrum hub adapter, `msg.value` must be at least `maxSubmissionCost + gasLimit · maxFeePerGas`. The relayer estimates these off-chain with the Arbitrum SDK.

`minGasL2` and `minGasL1` are constants, sized so receive handlers can't run out of gas: L2 release execution needs ≤ 150k; on L1, `receiveCheckpoint` only stores a hash. Messaging libraries: `@eth-optimism/contracts-bedrock` interfaces and `@arbitrum/nitro-contracts` (`AddressAliasHelper`, `IInbox`, `IBridge`, `IOutbox`).

## 8. Protocol flows

### 8.1 Deposit on Ethereum

1. **Wallet:**
   - Sample b and compute `P = H₂(pk, b)`.
   - Encrypt (a, b) to the user's own encPk.
   - Approve USDC for `DepositManager`.
2. **User:** call `DepositManager.deposit(a, P, encNote)`.
3. **Hub, in the same transaction:**
   - Compute `C = H₃(a, 1, P)` and insert `[C, Z₀]`.
   - `shieldedSupply += a`, `L[ETH] += a`.
   - Emit `L1Deposit(leafIndex, C, a, depositor, encNote)`.
4. **Wallet:** see the event and mark the note spendable at `leafIndex`.

The public sees: Ethereum, the depositor's address, a, the time and P. It learns nothing about future spends.

### 8.2 Deposit on Base or Arbitrum

1. **Wallet:** same note preparation as 8.1. Approve `a + settleFee` for the spoke.
2. **User:** `Spoke.deposit(a, P, encNote)`. The spoke stores the deposit at `index` and emits `Deposit`.
3. **Fast lane:**
   - Validators wait until the deposit's L2 block is at or below the L2 `finalized` head.
   - Each validator checks the deposit against its own L2 node, then signs a `DepositBatch` covering this and other recent deposits.
   - Any party, normally a validator, gathers a quorum and calls `DepositManager.submitAttestation`.
   - The hub inserts the leaves. Exposure is added. `L[c]` is unchanged.
4. **Slow lane, which always runs:**
   - Anyone calls `Spoke.sendCheckpoint()`.
   - After the bridge's delay, a finalizer proves and relays the message on L1, which calls `receiveCheckpoint`.
   - Anyone calls `processCheckpoint`. Each item is confirmed (fast) or inserted (slow). `L[c] += a + fee`.
5. **Wallet:** see `L2DepositInserted(chain, index, C, leafIndex, fastLane)` and mark the note spendable.

If the fast lane never attests a deposit (validators offline, capacity full, deposit above `maxFastDeposit`), step 4 inserts it. A deposit can never get stuck.

### 8.3 Spend: withdraw, partial withdraw, transfer, merge, fee-only

1. **Wallet:**
   - Sync the tree and nullifiers (Section 13.1).
   - Pick input notes, padding with a dummy if there's only one. Build the outputs: change, a note for the recipient, or zero.
   - Choose a fresh recipient address for withdrawals.
2. **Wallet:** check `available(dst) ≥ w`. Get a relayer quote (`relayer`, `relayerFee` rounded up to the bucket, and for Arbitrum the `BridgeParams` with the ETH value).
3. **Wallet:** fill in ExtData, including a deadline with random jitter. Compute `extDataHash` and `publicAmount`, then generate the Groth16 proof.
4. **Wallet → relayer, over Tor:** send `(proof, publicInputs, extData)`. The relayer simulates the call with `eth_call`, then submits `HubCore.transact{value}` with its own `BridgeParams`.
5. **HubCore:** run the checks from Section 7.4, then apply the effects:
   - nullifiers spent, outputs inserted, supply reduced
   - fees split
   - the release paid on Ethereum, or logged and sent through the official bridge
6. **Wallet:** scan the new outputs. Change and received notes become spendable. A transfer recipient's wallet finds its note by trial decryption.

### 8.4 Release on Base or Arbitrum

1. The official bridge delivers `MSG_RELEASE`: about 1–3 minutes on Base, about 10–15 minutes on Arbitrum (measure).
2. The spoke authenticates the origin. It then pays the recipient, or queues the release if liquidity is in flight.
3. If delivery fails, anyone can retry it on L2 (Arbitrum manual redeem, OP replay) or call `HubCore.resendRelease`.

Each release index executes at most once, so retries are always safe.

### 8.5 Why a note can't be spent on two chains

A malicious user builds proof A (to Base) and proof B (to Arbitrum) from the same note. Both carry the same nullifier N. Ethereum orders the two transactions:

- The first succeeds and adds N to the set.
- The second reverts with `NullifierSpent`.

Only one release is ever logged. Releases reach spokes only from HubCore through the official bridges, so no second payout can exist.

### 8.6 Rebalancing

1. A keeper sees `L[dst] < target[dst]` and `L[src] > target[src]`, then calls `LiquidityManager.rebalance(src, dst, m)`. Section 11.3 has the policy.
2. The hub updates `L[src] −= m` and `L[dst] += m − maxFee`. Then:
   - If `src = ETH`: the hub burns through CCTP directly.
   - Otherwise: it sends `MSG_REBALANCE` to the source spoke, which burns on arrival.
3. A keeper fetches Circle's attestation (`GET /v2/messages/{srcDomain}?transactionHash=…`) and calls `MessageTransmitterV2.receiveMessage` on the destination chain. The USDC mints to the destination vault.
4. Anyone calls `processQueue` on the destination spoke, if releases were queued.

### 8.7 LP add and remove (Ethereum only)

- **Add:** `addLiquidity(assets)` mints shares at the current price. `L[ETH] += assets`.
- **Remove:** `removeLiquidity(shares)` requires both:
  - `L[ETH] ≥ assets`
  - the safety valve still holds after removal: `unconfirmedFastValue ≤ β·(lpAssets − assets + insurance)`
  
  If either fails, the LP waits, or triggers a rebalance toward Ethereum.

### 8.8 Validator lifecycle

1. `register(signer)`, then `bond(amount ≥ s_min)`, then `setAllocations([Base, Arbitrum], [x, y])`. All of it takes effect at the next epoch.
2. Each epoch: watch the spokes, sign batches, gossip signatures, submit quorums, monitor others for equivocation and fraud, and earn rewards.
3. Exit: `requestUnbond`. The validator leaves the active set at the next epoch. After `τ_unbond`, if its remaining exposure is covered, it calls `withdrawUnbonded`.

### 8.9 Slashing flows

| Fault | Who detects | Proof | Effect |
|---|---|---|---|
| Mismatch (attested content differs from the canonical deposit) | Automatic, in `processCheckpoint` | Canonical checkpoint data | All batch signers fully slashed; the true leaf is inserted |
| Absence (attested deposit didn't exist at its block) | Any watcher | `proveAbsence` against a later checkpoint | All batch signers fully slashed |
| Equivocation (two different contents for one index) | Any watcher, from gossip | `proveEquivocation` with both signatures | Signer fully slashed |

### 8.10 Walkthrough: 1,000 USDC in, spent in pieces

| Step | Chain | Action | Public | Private |
|---|---|---|---|---|
| 1 | Base | Alice deposits 1,000 (fast lane) | Base, Alice's address, 1,000, settlement fee, time | Owner, blinding |
| 2 | Ethereum | Validators attest (~20 min later); leaf inserted | Batch, leaf index | — |
| 3 | Ethereum → Arbitrum | Withdraw 100 to fresh address B1 | 2 nullifiers, 2 commitments, w = 100, fees, Arbitrum, B1 | Which deposit; change 900 − fees |
| 4 | Arbitrum | Release delivered (~10–15 min); B1 receives 100 | B1, 100 | — |
| 5 | Ethereum | Private transfer of 300 to Bob | Nullifiers, commitments, relayer fee | Recipient, amount, link |
| 6 | Ethereum | Withdraw 500 to fresh address B2 on Ethereum | B2, 500, fees | Which deposit |
| 7 | Ethereum | ~7 days later: Base checkpoint processed; Alice's deposit confirmed; validators' exposure cleared; `L[Base] += 1,000 + fee` | Confirmation | — |

## 9. Validator network: security model and math

### 9.1 Notation (for chain c and epoch e)

| Symbol | Meaning |
|---|---|
| $s_v^c(e)$ | Stake that validator v allocated to chain c in epoch e (USDC) |
| $S^c(e) = \sum_v s_v^c(e)$ | Total stake allocated to c |
| $Q$ | Signer set of a batch; $S^c_Q = \sum_{v \in Q} s_v^c(e)$ |
| $A_B$ | Total amount of batch B |
| $e_v^c$ | v's current fast-lane exposure on c: value it has attested that is not yet confirmed |
| $k$ | Over-collateralization factor (default 1.5) |
| $\theta$ | Quorum fraction (default 2/3) |
| $\omega$ | Prover reward cap (default 10%) |
| $\beta$ | Safety-valve fraction (default 0.5) |

### 9.2 Quorum rules for a deposit batch (the md's R1–R3, applied to deposits)

$$\textbf{(R1)}\quad S^c_Q \ge \theta \cdot S^c \qquad\qquad \textbf{(R2)}\quad S^c_Q \ge k \cdot A_B$$

$$\textbf{(R3)}\quad \forall v \in Q:\quad e_v^c + x_v(B) \le \frac{s_v^c}{k}, \qquad x_v(B) = \left\lceil \frac{A_B \cdot s_v^c}{S^c_Q} \right\rceil$$

- **R1** is defense in depth: several independent validators must agree, which protects against a single buggy node. Safety does not depend on it.
- **R2** is the md's "bigger amounts need more stake". It follows from R3 (sum R3 over Q), but is kept as a cheap early check.
- **R3** is exposure accounting. Because $\sum_{v\in Q} x_v(B) \ge A_B$, the batch's full value is always charged to its signers.

Integer form, with k and θ as rationals $k = k_n/k_d$ and $\theta = \theta_n/\theta_d$: R1 is $\theta_d S_Q \ge \theta_n S$, R2 is $k_d S_Q \ge k_n A$, and R3 is $k_n (e_v + x_v) \le k_d\, s_v$.

### 9.3 Exposure lifecycle

| Event | Exposure change |
|---|---|
| Batch attested | $e_v^c \mathrel{+}= x_v(B)$ for each signer |
| **Every** item of B confirmed by canonical checkpoint data equal to the attested data | $e_v^c \mathrel{-}= x_v(B)$ |
| B proven fraudulent | All signers fully slashed and jailed; their exposure becomes moot |
| Time passing | **No change.** Exposure never clears on a timer |

That last row is the key difference from the md. In the md, exposure cleared when a window ended, so the cap only limited the *rate* of theft. Here it clears only on *verification*, so it limits the *total*.

### 9.4 Theorem: bounded validator damage (G6)

**Setting.**
- Honest validators sign only deposits they have checked against finalized L2 state.
- Let 𝔽 be the set of fraudulent batches, meaning batches with at least one item that differs from the canonical deposit or didn't exist at its claimed block.
- Let A be the set of validators that signed at least one batch in 𝔽. By definition, every signer of a fraudulent batch is in A.
- Let $F^c = \sum_{B \in 𝔽,\, B \text{ on } c} A_B$ and $F = \sum_c F^c$.

**Claim.**
1. At all times, $F^c \le S^c_A / k$ for every chain c. So $F \le S_A/k$, where $S_A = \sum_c S^c_A$ is at most A's total bonded stake.
2. Under A5 and A7, every $B \in 𝔽$ is eventually proven.
3. When B is proven, all of its signers' stake is slashed. Stake backing uncleared exposure can't be withdrawn beforehand. So total slashed is at least $S_A \ge k F > F$.
4. With prover reward $r = \min(\omega\Sigma,\ \Sigma - \text{coveredLoss})$, the protocol's net position after all proofs is at least 0.

**Proof.**

*Part 1.* A fraudulent batch can't have all of its items confirmed, so its exposure never clears before slashing. For each $v \in A$:

$$e_v^c \ \ge\ \sum_{B \in 𝔽_c,\ v \in Q_B} x_v(B)$$

Summing over A and using $\sum_{v \in Q_B} x_v(B) \ge A_B$ gives $\sum_{v\in A} e_v^c \ge F^c$. R3, together with the coverage rule (allocations can't drop below $k \cdot e_v^c$), gives $\sum_{v \in A} e_v^c \le S^c_A/k$.

*Part 2.* Take a fraudulent item at index i on chain c.
- If a canonical deposit exists at i, the checkpoint covering i yields a mismatch when it is processed.
- If no deposit existed at the claimed block, any checkpoint sent after that block with `countAtSend ≤ i` proves absence.
- If index i is filled later, its canonical `l2Block` is later than the claimed one, so the data differs: a mismatch.

Checkpoints are permissionless on L2 (empty ones are rate-limited), delivered by the official bridge (A5), and processed by anyone (A7).

*Parts 3 and 4.* Slashing takes the whole stake, and the coverage rule blocks withdrawals while exposure is uncleared. The prover cap guarantees $\Sigma - r \ge \text{coveredLoss}$. ∎

**What this means:** a coalition of any size, up to 100% of validators, can't profit and can't leave the pool short. In the worst case, the pool is temporarily illiquid by at most $\min(F, \beta \cdot (\text{lpAssets} + \text{insurance}))$ (Section 9.6) until the proof lands.

### 9.5 Slashing and loss coverage

- **Slash amount:** the validator's whole stake, both bonded and unbonding, written Σ.
- **Prover reward:** $r = \min(\omega \cdot \Sigma,\ \Sigma - \text{coveredLoss})$, where `coveredLoss` is the proven batch's fraudulent value. It is 0 for pure equivocation.
- **Remainder:** $\Sigma - r$ goes to insurance (USDC moved into the L1 vault; `L[ETH] += Σ − r`). It backs the fake notes' liabilities in `shieldedSupply`.
- **Jailing:** the validator is jailed permanently. Its operator and signer addresses can't register again.

### 9.6 Global safety valve

$$\text{unconfirmedFastValue} \le \beta \cdot (\text{lpAssets} + \text{insurance})$$

This rule is enforced on every attestation and every LP redemption. It caps how much fast-lane value can be unconfirmed at once, relative to the buffers that would absorb a temporary shortfall. It does not affect safety (Theorem 9.4); it limits temporary illiquidity.

### 9.7 Liveness

- **Fast lane:** works when validators holding at least θ of $S^c$ are online and honest, and capacity is available.
- **Everything else:** needs no validators (G9). That covers Ethereum deposits, the slow lane, every withdrawal and every release.

### 9.9 Fast-lane capacity

$$\text{Capacity}^c = \sum_v \Big(\frac{s_v^c}{k} - e_v^c\Big)$$

Capacity refills as checkpoints confirm, once per confirmation delay $T_{conf}(c)$.

*Example:* 7 validators each allocate 20,000 USDC to Base, for 140,000 in total. Capacity is about 93,333 USDC in flight, so on mainnet the fast lane can carry about 93k per ~7 days on Base. On Arbitrum Sepolia, where confirmation takes minutes, capacity is effectively unlimited.

### 9.10 Rewards

- **Validator pot:** `alphaV` × protocol fees accrue to the epoch pot. At `advanceEpoch`, the pot is split pro rata to each active validator's total allocated stake $\sum_c s_v^c$, then claimed through `claimRewards`.
- **Insertion bounties:** the attestation submitter earns `settleFee.insert` for each fast item once its batch is confirmed. The checkpoint processor earns `settleFee.final` per item, plus `insert` for each slow item.

Per-signature rewards are not used. The submitter can't steer payment.

## 11. Liquidity and solvency

### 11.1 Liquidity ledger

For each chain c ∈ {ETH, BASE, ARB}, `L[c]` is the hub's *conservative* count of free USDC in vault c.

| L[c] increases on | L[c] decreases on |
|---|---|
| Ethereum deposit (ETH, a) | Release reserved at spend time (dst, w) |
| Checkpoint confirmation of an L2 deposit (c, a + fee) | Payments on Ethereum: Ethereum withdrawals, relayer fees, claims, LP redemptions (ETH) |
| LP add; slashed stake moved in (ETH) | Rebalance out (src, m) |
| Rebalance in, counted at burn (dst, m − maxFee) | — |

Fast-lane deposits are **not** counted until they are confirmed.

### 11.2 Reservation rule

`transact` requires `L[dst] ≥ w` and reserves the amount atomically. Payments on Ethereum require `L[ETH] ≥ amount`; relayer fees and bounties fall back to claimable balances.

**Lemma.** For each spoke c: $V_c + M_c \ge L[c] + Q_c$, where:
- $V_c$ is the vault's USDC balance,
- $M_c$ is CCTP mints in flight toward c,
- $Q_c$ is releases and rebalance burns that were reserved but not yet executed.

*Sketch:* every increase of L[c] matches USDC already in the vault (confirmed deposits) or burned toward it (in-flight mints). Every decrease matches an outflow instruction that executes at most once. So a release can wait only for an in-flight mint (bounded by CCTP's attestation time), never for funds that don't exist.

### 11.3 Rebalancing policy [P0]

- **Targets:** $\text{target}[c] = \text{targetBps}[c] \cdot \sum_{c'} L[c'] / 10^4$. Defaults: ETH 3,000; BASE 3,500; ARB 3,500. The guardian can change them within bounds.
- **Who can rebalance:** anyone may call `rebalance(src, dst, m)` if all of these hold:
  - $m \ge \text{minRebalance}$
  - $L[src] - m \ge \text{target}[src]$ (the source has surplus)
  - $L[dst] < \text{target}[dst]$
  - $m \le \text{target}[dst] - L[dst]$
  
  So rebalancing always moves money from surplus to deficit, and griefers can't keep liquidity permanently in flight.
- **CCTP V2 calls:**
  - Burn with `depositForBurn(m, domain(dst), bytes32(vault(dst)), USDC, bytes32(0), maxFee, minFinalityThreshold)`, using `minFinalityThreshold = 2000` (Standard) and `maxFee = 0` by default.
  - Fast transfers (`1000`, with a fee) are allowed for ETH → L2 when `L[dst]` is critically low *(builder's call)*.
  - Domains: Ethereum 0, Arbitrum 3, Base 6. The same ids apply on testnets.

### 11.4 LP vault and loss waterfall

- LP shares use ERC-4626 math with a virtual offset. LPs earn alphaLP.
- **Loss waterfall** (for any shortfall):
  1. slashed stake (already in insurance)
  2. insurance
  3. LP assets, pro rata
  4. users
  
  Theorem 9.4 rules out step 4 under the stated assumptions. Reaching it would mean a bug or a broken assumption.

### 11.5 Insurance

It receives alphaIns and slashed remainders, and sits in the L1 vault, counted in `L[ETH]`. Nobody can withdraw it in v1 (no governance). It is a solvency buffer that backs fake-note liabilities and covers CCTP fee shortfalls.

### 11.6 Solvency invariant (enforced in tests, Section 15.3)

$$\underbrace{\sum_c V_c + M}_{\text{USDC held or in flight}} \;+\; \underbrace{\Sigma^{\text{pending}}}_{\text{stake of not-yet-proven fraudsters}} \;\ge\; \underbrace{Z}_{\text{shieldedSupply}} + Q + \text{lpAssets} + R$$

- R covers the reward pot, claimable balances and unpaid bounties.
- With no fraud, the two sides differ only by insurance (and rounding dust in the protocol's favor).

### 11.7 USDC-specific risks (accepted; documented for peers)

- Circle can blacklist a vault address or pause USDC. Circle froze USDC held in Tornado Cash-linked addresses in 2022.
- USDC could depeg.
- CCTP outages delay rebalancing, but never break safety.
- A blacklisted *recipient* makes that release fail. It is recorded as failed and retryable, and the rest of the queue keeps moving.

## 12. Privacy specification

The cryptography makes every withdrawal indistinguishable from any other spend against the same root (S9). In practice, privacy is lost through metadata: amounts, timing, addresses, gas and IP. v1 therefore enforces good habits by default.

### 12.1 What is public

See ℒ in Section 4.5. Three properties matter most:

- **One global set.** A withdrawal on any chain can come from any deposit on any chain, so cross-chain use widens the set of possible sources instead of splitting it.
- **Chain choice is metadata.** The deposit chain and the withdrawal chain are both public. The metrics below must treat chain choice as a signal an adversary can use.
- **Some timing is fixed by the protocol.** Fast and slow deposits become spendable at known times, and the wallet's delay rules take that into account.

### 12.2 Anonymity metrics [P1: measurement tool; P0: definitions]

**Cryptographic set.** For a spend against root R, the candidate sources are all leaves with index < `leafCount(R)`. This is the set the proof hides within. It is not a meaningful privacy measure on its own, because leaves include change notes, zero-value padding and dummy outputs whose amounts nobody can see.

**Deposit-provenance anonymity.** This is the measure that matters. Model the public data as a flow problem: each withdrawal (w, chain, time, fees) must be funded by the deposits made before it, net of earlier withdrawals.

- An adversary assigns each candidate deposit d a posterior $p_d$ using heuristics: amount feasibility (including partial-withdrawal sums), timing decay, address clustering, chain priors and fee fingerprints.
- From that posterior, report:

$$k_{feas} = \lvert\{d : d \text{ not excluded}\}\rvert, \qquad H = -\sum_d p_d \log_2 p_d, \qquad k_{eff} = 2^{H} \le k_{feas}$$

**[P1] Headline experiment.** Replay real public traces (Tornado Nova on Gnosis Chain, Railgun, Privacy Pools) mapped onto three chains. Compare $k_{eff}$ for:
- (a) one global pool (xpool)
- (b) three separate per-chain pools under the same traffic

Report the median and 10th percentile, with and without the wallet protections below. This is the evidence for "cross-chain makes privacy stronger". Method: Guo & Feng 2026, "The Anonymity Gap"; Wang et al. 2023; Tutela.

### 12.3 Wallet protections (defaults) [P0 unless marked]

| # | Default | Override |
|---|---|---|
| W1 | Spends go only through a relayer; never sent from the user's own address | `--self-relay --i-understand-linkability` |
| W2 | Every withdrawal goes to a fresh recipient derived from the separate HD path (Section 5.3). Recipients are never reused, and never set to the depositor's address or any address it has interacted with (checked against local history) | explicit flag |
| W3 | Minimum delay since the funding deposits: default 24 h. Warn below that; block below 1 h | flag |
| W4 | Minimum anonymity: warn if fewer than 20 deposits were made after the funding deposit ($k_{feas}$ estimate); block below 5 | flag |
| W5 | Amount hygiene: suggest round amounts (10, 50, 100, 500, 1k, 5k, 10k); warn when a withdrawal is within 1% of a deposit amount; offer to split into several withdrawals at random delays (scheduler) | — |
| W6 | Merge notes before withdrawing, to avoid fingerprints from partial-withdrawal sums | — |
| W7 | Fee buckets (also enforced on-chain) | — |
| W8 | Tor: relayer calls, and RPC calls where possible, go through a Tor SOCKS5 proxy when one is available; loud warning when Tor is off | `--no-tor` |
| W9 | Full sync: download every relevant event. Never ask a remote RPC about the user's own notes (no per-note `isSpent` calls, no filtered `getLogs` by commitment). Spread queries over several RPCs; support a local node | — |
| W10 | Deadline jitter: a random deadline inside the window, and random submission delay | — |
| W11 [P1] | Gas for a fresh address: built-in helper that pays gas in USDC through Circle Paymaster (ERC-4337 v0.7/v0.8 or EIP-7702) on Base, Arbitrum and Ethereum, so the fresh address never has to be funded from a known one | — |
| W12 | Change notes are always encrypted to self; dummy outputs are indistinguishable from real ones | — |

### 12.4 Protocol-level protections [P0]

- Relayer fees must fall in buckets (Section 10.5).
- The settlement fee is fixed per chain.
- Every withdrawal goes through the same release path per destination.
- extData carries a deadline, so a relayer can't hold a proof and replay it at a time of its choosing.
- No lane choice is exposed to users, so lane can't fingerprint them.

### 12.5 What v1 does not hide (stated plainly)

- Deposit amount, time, chain and depositor address.
- Withdrawal amount, time, chain and recipient.
- That someone used xpool at all.
- Aggregate flows between chains.
- Network metadata, unless the user uses Tor.

Users who withdraw an exact deposit amount soon afterwards, on a quiet day, can still be linked by amount and timing. W3–W6 exist to make that hard by default.

|---|---|

### 13.5 Finalizer [P0]

- Calls `Spoke.sendCheckpoint` on a schedule: every N deposits or T minutes, and an empty checkpoint when watchers need one.
- **OP Stack:** waits for a dispute game covering the L2 block, proves the withdrawal (viem OP Stack actions), waits out the maturity delay, then finalizes.
- **Arbitrum:** waits for assertion confirmation, then calls `Outbox.executeTransaction` with the proof (Arbitrum SDK).
- Then calls `processCheckpoint` in chunks.
- Also monitors and re-delivers releases (shared logic with the relayer).

### 13.6 Rebalancer keeper [P0]

- Polls `L[c]` and the targets, and calls `rebalance` when the policy allows.
- Completes CCTP mints: fetches the attestation from Circle's API (the sandbox endpoint on testnet), then calls `receiveMessage`.
- Calls `processQueue` on spokes.

### 13.7 Observability [P1]

- Every service exposes Prometheus metrics: fast-lane capacity, `unconfirmedFastValue`, `L[c]`, release delivery latency, checkpoint backlog, failed messages and slashing events.
- A Grafana dashboard JSON is included.
- Alerts fire on: any fraud proof, delivery older than 1 h, `L[c]` below 10% of target, and `unconfirmedFastValue` above 80% of the valve.

## 15. Testing and validation plan

### 15.1 Circuit tests [P0]

**Positive cases:**
- full withdrawal
- partial withdrawal
- transfer
- merge
- fee-only
- dummy input
- both inputs real
- maximum amounts ($2^{248}-1$ on an output)
- deepest leaf index ($2^{24}-1$)

**Negative cases** (each must fail):
- wrong root
- wrong path
- wrong sk
- duplicate nullifiers
- output amount ≥ $2^{248}$
- input amount ≥ $2^{248}$
- leaf index ≥ $2^{24}$
- an unbalanced equation in either direction
- tampered extDataHash
- non-zero amount with a bad path
- a wrapped amount: an input that is p − x posing as a small value, or similar

**Consistency checks:**
- Poseidon vectors identical across circom, the SDK and Solidity (Section 5.2).
- Nullifier and commitment vectors identical between the SDK and the circuit.
- Constraint count recorded in CI.

### 15.2 Contract unit tests [P0]

Every function in Section 7, on both success and revert paths. That includes every `transact` check, all three deposit routes, every fraud-proof type, every guardian power and its limits, rebalancing policy edges, LP inflation-attack resistance, and adapter authentication (wrong messenger, wrong cross-domain sender, unaliased caller).

### 15.3 Fuzz and invariant tests (Foundry, ≥ 10⁶ calls each) [P0]

| ID | Invariant |
|---|---|
| I1 | No nullifier is accepted twice |
| I2 | `shieldedSupply` = Σ inserted deposit amounts − Σ v over spends |
| I3 | Solvency (Section 11.6) holds in every state |
| I4 | For every spoke: $V_c + M_c \ge L[c] + Q_c$ (Lemma 11.2) |
| I5 | Each (chain, index) L2 deposit is confirmed at most once and credited to L[c] at most once |
| I6 | For all v and c: $k \cdot e_v^c \le s_v^c$ |
| I7 | Release indices per destination are contiguous; each executes at most once on the spoke |
| I8 | Only the canonical adapters can trigger releases, rebalances or pauses on spokes |
| I9 | The guardian can't reduce any vault balance, and can't block `transact` for more than 72 h per 30 days |
| I10 | Stake backing non-zero exposure can't be withdrawn |
| I11 | `nextIndex` is even; the root history is consistent with the inserted leaves (recomputed by a reference implementation) |
| I12 | Theorem 9.4: net protocol position after all fraud proofs ≥ 0, for random collusion strategies |

### 15.4 Local integration matrix [P0]

Run all of these through `make e2e`:

- Deposits on each of {ETH, BASE, ARB}, through both lanes.
- Withdrawals to each of {ETH, BASE, ARB}.
- Transfers and merges.
- The same note proven for two destinations at once: the first succeeds and the second reverts.
- A queued release, then a rebalance mint arrives, then `processQueue`.
- Delivery failure (gas too low), then retry, then `resendRelease`.
- Fast lane with validators offline: everything finishes through the slow lane.

### 15.5 Adversarial suite [P0]

| Scenario | Expected result |
|---|---|
| 100% of validators sign fake deposits up to capacity, then spend them | Inserted fake value ≤ S/k. Mismatch fraud is proven at the checkpoint. All signers are slashed. Net protocol position ≥ 0 (I12) |
| A coalition attests a non-existent future index | Absence proven using an empty checkpoint; slashed |
| A validator signs two different contents for one index | Equivocation proven from gossip; slashed |
| A coalition tries to unbond before its fraud is proven | Blocked by exposure coverage (I10) |
| Relayer changes recipient or fee | Proof fails |
| Relayer holds a proof past its deadline | Rejected |
| Front-runner copies a pending `transact` | Same outcome; the front-runner gains nothing |
| L1 or L2 reorg before finality (simulated) | Validators don't attest; canonical messaging is unaffected |
| CCTP attestation delayed | Releases queue, then complete once the mint lands |
| USDC blacklists a recipient (mock) | That release is marked failed; others proceed |
| LP rushes to exit while fast-lane value is unconfirmed | Safety valve blocks the excess |
| Griefing with rebalances | The policy allows only surplus → deficit moves |
| Spam of empty checkpoints | Rate-limited |
| Deposit or spend when the tree is full (test with a small-depth build) | Reverts cleanly with `TreeFull` |

## 16. Mainnet readiness gates

These come before any real-money deployment. The team decides when each is met.

1. **Audits:** two independent audits covering contracts, circuits, adapters, Poseidon libraries and off-chain signers. All critical and high findings fixed and re-reviewed.
2. **Trusted setup:** the phase-2 MPC ceremony is complete (Section 6.7). Transcripts are public and verified.
3. **Testnet soak:** at least 2 weeks with no invariant alerts, the full Section 15.6 matrix passed, and a public "break it" period completed.
4. **Guarded caps:** `maxDeposit`, `maxFastDeposit`, TVL caps per chain and β set conservatively. Raise them only within the hard bounds.
5. **Monitoring and response:** alerts live and an incident runbook written. The guardian Safe has at least 3 signers, including at least one external.
6. **Legal review:** the roles that operate infrastructure (relayers, validators, LPs, keepers) and the team's jurisdictions. Privacy tools carry real legal risk:
   - Tornado Cash was under OFAC sanctions from 2022 until its 2025 delisting.
   - Its developers were prosecuted.
   - Decide the relayer and front-end policy explicitly.
7. **Bug bounty** live.

## 21. Glossary

| Term | Meaning |
|---|---|
| Note | A private record (amount, token, owner key, blinding) owned by one spending key |
| Commitment C | Public hash of a note; a leaf in the tree |
| Nullifier N | Public tag revealed when a note is spent. It blocks double spends without revealing which note was spent |
| Owner digest P | $H_2(pk, b)$. Sent at deposit; hides the owner |
| Join-split | A spend that consumes 2 notes and creates 2, conserving value |
| Hub | The Ethereum contracts that hold the global tree, nullifiers, release log, stake and the Ethereum vault |
| Spoke | The contract on Base or Arbitrum that holds USDC, takes deposits and executes releases |
| Release | A hub-logged instruction to pay w to a recipient on a destination chain |
| Canonical / official bridge | A rollup's built-in messaging with Ethereum (OP Stack messengers; Arbitrum inbox and outbox) |
| Checkpoint | A spoke → hub canonical message listing deposits, used to confirm or insert them |
| Fast lane | Validator attestations that make L2 deposits spendable before the checkpoint arrives |
| Slow lane | Inserting L2 deposits from canonical checkpoints, with no validators |
| Exposure $e_v^c$ | Value validator v has attested on chain c that isn't yet confirmed |
| Allocation $s_v^c$ | Part of v's bonded stake assigned to back chain c |
| Quorum R1–R3 | The stake rules a batch must meet (Section 9.2) |
| Safety valve β | Cap on total unconfirmed fast-lane value, relative to LP assets plus insurance |
| L[c] | The hub's conservative count of free USDC on chain c |
| CCTP | Circle's Cross-Chain Transfer Protocol (burn and mint of native USDC) |
| Relayer | A service that submits spends and pays gas for a fee, so users never use a linkable address |
| Finalizer | A service that carries checkpoints across the bridges and redelivers messages |
| ℒ | The leakage function: exactly what is public (Section 4.5) |
